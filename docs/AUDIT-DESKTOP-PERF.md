# Аудит отзывчивости KinoTrend Desktop 2.3.8

Дата: 2026-11-19
Объект: `desktop/` — Kotlin 2.1.21 + Compose Desktop 1.8.2, сборка 2.3.8
Задача: убрать задержку между кликом «Смотреть» и запуском плеера.

---

## 1. Как это измерялось

Три независимых источника фактов:

1. **Живые логи запущенного приложения** — `KinoTrend/data/player.log` и
   `KinoTrend/data/torrserver/torrserver.log` (портативная сборка, сессия 2026-11-19).
   Логи пишутся самой программой, поэтому это точные тайминги кликов.
2. **Стенд A/B** — `desktop/src/test/kotlin/app/kinotrend/desktop/bench/WatchBench.kt`.
   В нём воспроизведён **старый** код (глобальный монитор `TorrServerManager`) и
   **новый** код, оба против настоящего TorrServer 1.2.34.
3. **Проверка патча** — `bench/TimeoutCheck.kt`: подтверждает, что TorrServer
   действительно подхватывает изменённый `TorrentDisconnectTimeout`.

## 2. Что показали логи реального запуска

`KinoTrend/data/player.log`, 2026-11-19 (время UTC):

```
11:40:37  TorrServer: add torrent magnet:?xt=urn:btih:afa55267…   ← предзагрузка
11:40:38.457  play: start TorrServer                                ← клик «Смотреть»
11:40:43.414  play: server ready                                    ← клик отработал через 4957 мс
11:40:43.414  play: launching player
```

`KinoTrend/data/torrserver/torrserver.log` за те же секунды:

```
11:40:37  add torrent magnet:?…afa55267…      ← предзагрузка уже добавила магнит
11:40:42  Create cache for: Guarding.Stars…   ← метаданные разрешились только здесь
11:40:43  add torrent magnet:?…afa55267…      ← клик добавляет тот же магнит ВТОРОЙ раз
11:40:50  Torrent close by timeout 9d85aa49…   ← предзагрузка протухает через 30-60 с
```

Отдельный факт: `POST /torrents {action: add}` сам по себе отвечает за **96 мс** —
сеть тут не при чём. Значит 4957 мс клик ждал **не сеть, а монитор в коде**.

### 2.1. Проверка на живой сборке (2026-11-19, 12:17 UTC)

Тот же сценарий в пересобранном приложении — пользователь открыл карточку фильма
и через секунду нажал «Смотреть»:

```
12:17:10  TorrServer: add torrent magnet:?…62eb683f…    ← предзагрузка раздачи 1
12:17:10  TorrServer: add torrent magnet:?…a8face8b…    ← предзагрузка раздачи 2 (параллельно)
12:17:13  Create cache for: Speed.Demon…MegaPeer.mkv 62eb683f…
12:17:13  Create cache for: Speed.Demon…1080p.mkv    a8face8b…
12:17:11.877  play: start TorrServer                    ← клик «Смотреть»
12:17:13.691  play: stream ready in 1814 ms
12:17:13.901  play: player alive in 2023 ms              ← VLC пошёл, D3D11VA
```

Два факта, которых раньше не было:

1. **Дубля `add torrent` больше нет.** В старом логе на одну раздачу всегда шли
   две записи (`11:40:37` — предзагрузка, `11:40:43` — клик). В новой сессии на
   каждую раздачу ровно одна запись: клик взял уже подготовленный результат.
2. **Обе раздачи фильма готовятся параллельно** — раньше предзагружалась только
   одна, да и её результат выбрасывался.

Клик отработал за 1814 мс, потому что был сделан, пока шла предзагрузка: он
дождался **той же самой** подготовки (3631 мс от её начала) и сразу получил
поток. В старом коде к этому времени добавился бы ещё и повторный `add`
раздачи (~1400 мс по логу от 19.11) — то есть клик занял бы около 3.2 с.

## 3. Корневые причины

### 3.1. Глобальный монитор `synchronized(lock)` — главная причина «долго срабатывает»

Старый `TorrServerManager` держал **один монитор на весь класс**:

- `prepare()` — внутри монитора опрашивает `file_stats` до 60 раз по 500 мс (до 30 с);
- `ensureStarted()` — внутри монитора ждёт старта сервера до 30 с;
- `start()` и `addHash()` — тоже под тем же монитором.

Клик «Смотреть» вызывал `start()`, а тот вставал в очередь на монитор, который
удерживала **фоновая предзагрузка**. Клик висел ровно столько, сколько шла
предзагрузка — в логе это 4957 мс, и это **полностью совпадает** с моментом
`Create cache` (11:40:42), когда предзагрузка отпустила монитор.

### 3.2. Предзагрузка готовила раздачу впустую

`DetailsScreen` вызывал `TorrServerManager.prepare(best.magnet)`, получал
правильный URL с найденным индексом видеофайла — и **выбрасывал результат**,
оставив от него только буферизацию. Клик затем шёл другим путём (`addHash`),
то есть делал ту же работу второй раз.

### 3.3. Клик и предзагрузка работали с разными URL

Предзагрузка буферизовала `/stream/<имя файла>?…&index=1`, а клик открывал
`/stream?link=…&index=0` — без имени файла и с другим индексом. Для
однофайловых раздач TorrServer это эквивалентно (проверено: оба URL отдают
`HTTP 206 video/x-matroska` с одинаковым началом файла), но для многофайловых
раздач `index=0` — не тот файл, что был подготовлен. Прогретый кэш при этом
не использовался.

### 3.4. Предзагрузка протухала раньше, чем приходит пользователь

TorrServer по умолчанию выбрасывает неактивный торрент через 30 с
(`TorrentDisconnectTimeout: 30`), что видно в логе как `Torrent close by timeout`.
К моменту клика подготовленный кэш часто уже был выброшен.

### 3.5. Фиксированная пауза `delay(1500)`

После запуска процесса плеера код всегда ждал 1500 мс перед тем, как показать
статус «Плеер запущен» — независимо от того, запустился плеер за 20 мс или нет.

### 3.6. Перерисовка каталога на каждое нажатие

`AppState.filteredMovies`, `allGenres`, `allCountries` — обычные геттеры. Они
пересчитывались на **каждой** рекомпозиции, а `state.filteredMovies` читался
прямо в теле композабла `HomeScreen`. Каталог — 144 фильма, но на каждое
нажатие в поиске он фильтровался и сортировался заново.

### 3.7. Загрузка постеров

- `memory` — обычный `HashMap`, который читался без синхронизации при записи
  под `synchronized` — гонка данных;
- одинаковые запросы не схлопывались: `Backdrop` и `Header` на карточке фильма
  грузили один и тот же `bigPosterURL` дважды;
- полноразмерные постеры декодировались и навсегда оставались в памяти;
- имя файла кэша строилось из `url.hashCode()` — коллизии давали бы чужой постер.

### 3.8. Экран плеера перерисовывался четырежды на тик

`PlayerScreen` писал четыре отдельных `mutableState` каждые 300 мс.

## 4. Что изменено

| Файл | Изменение |
|---|---|
| `data/TorrServerManager.kt` | Глобальный монитор заменён на `startLock` (только старт процесса) + per-magnet блокировки. Добавлен кэш `preparedCache` (magnet → URL с найденным индексом). Хэш берётся из самого магнита (`hashFromMagnet`) без обращения к серверу. Если сервер уже знает хэш — используется `action=get` вместо повторного `action=add`. `TorrentDisconnectTimeout` поднимается 30 → 900 с. Shutdown-hook не убивает сервер, если недавно запущен внешний плеер. |
| `ui/AppState.kt` | `playTorrent` берёт готовый URL из кэша вместо повторного `add`; `delay(1500)` заменён на ожидание появления процесса с выходом сразу; добавлен лог тайминга. `filteredMovies`, `allGenres`, `allCountries` переведены на `derivedStateOf`. |
| `ui/DetailsScreen.kt` | Предзагрузка готовит **все** раздачи фильма параллельно (была одна, с выброшенным результатом). |
| `ui/PosterLoader.kt` | Потокобезопасный LRU-кэш с ограничением, дедупликация одинаковых загрузок, масштабирование битмапа, имя файла кэша по SHA-1. |
| `ui/PlayerScreen.kt` | Четыре состояния объединены в одно — одна рекомпозиция на тик вместо четырёх. |
| `src/test/.../bench/` | Стенд A/B и проверка патча — в test-наборе, в поставку не попадают. |

## 5. Результат

Стенд A/B против настоящего TorrServer, тот же магнит, тот же сценарий:

| Сценарий | Было | Стало |
|---|---|---|
| Клик «Смотреть» по прогретой раздаче | 613 мс | **0 мс** |
| Клик, пока предзагрузка ещё идёт | 1636 мс | **1229 мс** |
| Разрешение метаданных (теперь в фоне, не на клике) | 2868 / 11372 мс | то же, но вне клика |
| Старт TorrServer (первый / повторный) | 1920 мс | 1920 / 59 мс |
| Хэш из магнита | — | 15 мс, без сети |

Проверка патча:

```
settings.json до старта:   TorrentDisconnectTimeout=30
start(): 606 ms
settings.json после старта: TorrentDisconnectTimeout=900
патч применён: true
```

И в рантайме TorrServer:

```
"Client config": … "TorrentDisconnectTimeout":30    ← было
"Client config": … "TorrentDisconnectTimeout":900   ← стало
```

Что это значит на практике:

- **Карточка фильма открыта, предзагрузка успела — клик мгновенный (0 мс).**
  Раньше клик ждал завершения фонового опроса метаданных (в логе 4957 мс).
- **Клик сделан сразу, пока предзагрузка ещё идёт** — клик ждёт *ту же самую*
  общую подготовку, а не начинает вторую; лишний повторный `add` убран.
  Подтверждено на живой сборке: дубля `add torrent` в логе больше нет.
- Плеер получает URL с **найденным индексом видеофайла** и его именем, и
  прогретый кэш TorrServer используется по назначению.
- Подготовленная раздача больше не протухает через 30 с — живёт 15 минут.
- Внешний плеер не теряет соединение при закрытии приложения в течение 10 минут
  после запуска playback.

### 5.1. Что изменилось в поставленной сборке

- `desktop/build/compose/binaries/main/app/KinoTrend/` — пересобранный дистрибутив.
- `KinoTrend/app/` — портативная сборка обновлена (новый jar приложения и
  `skiko-awt-runtime`; старые удалены, `KinoTrend.cfg` пересчитан).
- Данные профиля (`KinoTrend/data/`) сохранены; в `settings.json` TorrServer
  теперь `TorrentDisconnectTimeout: 900`.

## 6. Что осталось (не входит в этот проход)

1. **Встроенный трейлер-плеер** стартует ~1.8 с: 207 мс на подъём JavaFX-тулкита,
   622 мс на резолв варианта HLS, 1093 мс на создание медиа (`player.log`).
   Ускоряется преинициализацией JavaFX при открытии окна, а не при первом
   воспроизведении.
2. **`AppState.persist()`** пишет `preferences.json` на главном потоке. Файл
   маленький (~1 КБ), но вызывается на каждом переключении фильтра.
3. **Рост каталога.** При 144 фильмах фильтрация незаметна; при тысяче и больше
   понадобится индекс по названию вместо полного прохода.
4. **Скорость самого торрент-потока** (первые байты, число пиров) приложению не
   поддаётся — это вопрос трекеров и раздачи.
5. **Поток в памяти TorrServer** — 64 МБ (`CacheSize`). Для нескольких
   одновременных раздач может не хватить.

## 7. Как перепроверить

```powershell
cd "<project>\desktop"
.\gradlew.bat --offline compileTestKotlin

# A/B замер клика (поднимет TorrServer и добавит тестовые раздачи)
java -cp "build\classes\kotlin\main;build\classes\kotlin\test;<project>\KinoTrend\app\*" `
  app.kinotrend.desktop.bench.WatchBenchKt

# проверка патча TorrentDisconnectTimeout
java -cp "build\classes\kotlin\main;build\classes\kotlin\test;<project>\KinoTrend\app\*" `
  app.kinotrend.desktop.bench.TimeoutCheckKt
```

Тайминги самой программы пишутся в `data/torrserver-client.log`
(`prepare … ms hash=… index=…`) и в `data/player.log`
(`play: stream ready in … ms`, `play: player alive in … ms`).
